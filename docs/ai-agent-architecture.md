# AI Agent Architecture

## Integration boundary

The checked-in application was a React/Vite frontend with localStorage ticket persistence. It did not contain a Node API, database, or authentication implementation. The backend in `server/` is added alongside the existing frontend rather than replacing its pages. SQLite is the server-side system of record for authenticated accounts, tickets, workflow state, and audit events. The React app no longer creates or edits tickets in localStorage.

## Request lifecycle

1. A student signs in with a locally managed account. The server issues a random opaque session token in an HttpOnly, SameSite=Strict cookie. Only an administrator provisioned from server environment variables can use the staff dashboard.
2. The student completes the existing issue form, including an optional needed-by date, and selects **Analyze & Review with AI**. This creates a workflow record; it does not create a complaint.
3. The Manager Agent asks Gemini for a structured plan and delegates classification, priority, resolution, and routing in parallel.
4. Specialist outputs are constrained to the current category, priority, department, support-team, and issue-type choices. Priority uses Low, Medium, High, or Critical. The student-selected priority is evidence of a request, not the assigned result.
5. The Resolution Agent may select only FAQ items marked `verified: true` and accompanied by an HTTPS `sourceUrl`. It can return exact excerpts only; deterministic validation rejects any excerpt not present in the approved source. The current bundled FAQ content has no provenance, so all of it is disabled for AI recommendations until reviewed and approved.
6. The Validation Agent checks structured fields, consistency, source grounding, and Gemini's review. If approved, the Manager Agent combines only accepted structured values and exact FAQ excerpts into a deterministic summary. Workflow and per-agent states/events are persisted as they change.
7. The UI displays the actual run states and results. A separate **Confirm and Submit Complaint** action calls the server's confirmation endpoint. Only an owned, approved, unexpired workflow can create a ticket. The transaction creates one ticket per workflow; repeat confirmation returns the existing ticket and ID.

## Modules

- `server/api.js`: Express API, validation, rate limits, authentication/role middleware, owner scoping, complaint actions, and workflow endpoints.
- `server/auth.js`: scrypt password hashes, opaque session tokens stored as SHA-256 hashes, cookie helpers, and environment-provisioned admin.
- `server/database.js`: SQLite schema, transactions, and append-only audit entries. The database is accessed only by backend services.
- `server/gemini-client.js`: Gemini JSON mode, server-only API key header, retry/backoff for quota and transient failures, and a process-wide request-rate guard.
- `server/agents/manager-agent.js`: Gemini planning and final synthesis.
- `server/agents/classification-agent.js`: broad type and existing helpdesk category.
- `server/agents/priority-agent.js`: urgency, deadline signal, and rationale.
- `server/agents/resolution-agent.js`: exact excerpts from approved FAQ sources only.
- `server/agents/routing-agent.js`: existing department/team pairs, with assignees attached by server configuration rather than generated by Gemini.
- `server/agents/validation-agent.js`: schema, configured department/team/assignee consistency, and FAQ source-grounding checks.
- `server/orchestrator.js`: persisted state transitions, parallel specialists, failure handling, and safe workflow input validation.
- `server/complaints.js` and `server/tickets.js`: confirmation-gated ticket creation, one-time migration behavior, ID generation, and owner-filtered reads.
- `src/utils/api.js`: same-origin authenticated frontend requests.
- `src/components/AIAgentActivity.jsx`: persisted agent states, results, current task, and event history.
- `shared/helpdesk-data.js`: categories, statuses, departments, teams, and existing FAQ text shared by frontend and backend to prevent routing/validation drift.

## Data and access rules

- Student ticket reads are filtered by `owner_user_id` from the session, not by a client-supplied email or ID.
- Admin-wide reads, updates, status changes, exports, and deletion require the administrator role.
- Student registration always creates the `student` role. There is no public admin signup or role-change endpoint.
- Ticket owner name/email are taken from the authenticated account on confirmation. Agents never receive credentials or direct database access.
- The legacy import accepts only the signed-in student's matching email, is one-time per account, validates fields, and retains the original browser data. Because localStorage could have been edited by its owner, imported historical fields are treated as user-provided legacy records, not independently authenticated institutional records.
- `audit_log` stores actor, action, entity, and timestamp, but not complaint prompts, passwords, session tokens, or API keys.
- Status values remain Pending, In Progress, and Resolved. Legacy Urgent priority is normalized to Critical.
- Routing pairs and their assignees are configured in `shared/helpdesk-data.js` from the existing example-ticket assignments. The Routing Agent sees department/team pairs only; deterministic code adds the exact configured assignee. Pair mismatches and any non-configured assignee are rejected by routing and validation. These legacy example assignments are the application's current source of truth, not independent confirmation of university staffing.

## API surface

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`
- `GET /api/tickets`, `POST /api/tickets/import-local`, `GET /api/tickets/migration-status`
- Admin-only `PATCH /api/tickets/:ticketId/status`, `PATCH /api/tickets/:ticketId`, and `DELETE /api/tickets/:ticketId`
- `POST /api/ai/workflows`, `GET /api/ai/workflows`, `GET /api/ai/workflows/:workflowId`
- `POST /api/ai/workflows/:workflowId/confirm` (explicit confirmation is required)
- `GET /api/health`

API responses are not cacheable. Mutations check the configured request origin; session cookies are Secure in production.

## Configuration and limits

Copy `.env.example` to `.env`. Set `GEMINI_API_KEY`, `ADMIN_EMAIL`, and a strong `ADMIN_PASSWORD`; optionally set `ADMIN_NAME`, `GEMINI_MODEL`, `GEMINI_REQUESTS_PER_MINUTE`, `DB_PATH`, `PORT`, `APP_ORIGINS`, and `NODE_ENV`. The API key is read only by the Node process and is never exposed through Vite.

Each successful workflow uses six Gemini calls (manager plan, four parallel specialists, and validation). Manager synthesis is deterministic and constrained to validated structured results, so it adds no provider call or new factual advice. The process allows one active workflow and defaults to eight provider requests per minute. A 429/5xx/network timeout is retried a bounded number of times; failures mark the workflow failed and do not create a complaint. The configured and default model is `gemini-3.6-flash`; confirm model access and quota for the API-key project before deployment.

## Known deployment limitations

- Local email/password accounts do not verify university affiliation. Connect the institution's SSO/OIDC provider before using the system as a university identity boundary.
- The original FAQ content is demo data without provenance. No AI resolution advice is enabled by default. Populate and approve official FAQ sources in `server/config.js` before relying on resolution suggestions.
- SQLite is suitable for a single-instance deployment. Multi-instance hosting needs a shared transactional database and a distributed workflow/quota coordinator.
- Protect the SQLite file with deployment-level encryption, backups, retention rules, and access controls.
- Live browser/API verification was not possible in the sandbox because loopback TCP connections were denied. Service-level tests exercise the orchestration, ownership, approval, migration, and idempotency paths without opening a network socket.

## Tests

`npm test` runs Node's built-in test runner. The suite covers each agent, structured Gemini request and retry behavior, local password/session handling, student/admin ticket visibility, one-time owner-filtered migration, persisted workflow state, confirmation gating, and duplicate-confirmation idempotency. Provider results are deterministic test doubles only; production has no fallback response.
